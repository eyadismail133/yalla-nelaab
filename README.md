# يلا نلعب — منصة ألعاب عربية جماعية للموبايل

لعبة أونلاين لـ 2–8 لاعبين بكود غرفة أو لينك مباشر، موجهة للقعدات ولماتشات الأصحاب. **الماتش مش مجرد أسئلة اختيارات** — ده خليط متوازن من 18 نوع جولة مختلف، كل نوع بآلية تفكير ونقط وشكل مختلفين تمامًا عشان اللعب يفضل ممتع ومفتوح للمنافسة لآخر لحظة.

الواجهة عربية بالكامل بتصميم RTL وباللهجة المصرية، وبنك الأسئلة مكتوب بالإيد (8,901 سؤال في 14 مجال).

---

## نمطا التشغيل والإطلاق

المنصة مبنية لتدعم خيارين للاتصال والتشغيل من نفس الكود المصدري:

1. **نسخة البيتا السحابية المجانية (Firebase Spark Beta):**
   - تعمل بنظام خادم سحابي بدون تكلفة (Serverless) موجه للقعدات الخاصة بين الأصدقاء.
   - **سبب اختيار Firebase Spark:** تم فحص استضافة Render، ووجد أن مسار النشر هناك يتطلب إدخال بطاقة بنكية («Add Card»). ولضمان إطلاق بيتا مجاني 100% بدون أي بطاقة دفع، ولا فترات تجريبية، ولا موارد مدفوعة، تم اعتماد خطة Firebase Spark كبديل معتمد.
   - **الخدمات المعتمدة:** Firebase Hosting (لتقديم ملفات الويب الثابتة)، وAnonymous Authentication (لتسجيل الدخول المجهول بهويات مؤقتة للاعبين)، وRealtime Database في منطقة `europe-west1` (لتزامن الحالة وحراسة الأمان).
   - **بدون تكاليف إضافية:** لا يتم استخدام Cloud Functions (لأنها تتطلب ترقية Blaze ببطاقة دفع)، ولا Cloud Storage، ولا أي خوادم مدفوعة.
2. **نسخة السيرفر المحلي والذاتي (Local Node + Socket.IO):**
   - سيرفر كامل مدمج في المشروع (`apps/server`) يجمع بين محرك اللعبة وسيرفر الويب وSocket.IO للتطوير المحلي، أو للعب عبر الشبكة الداخلية (LAN)، أو للنشر الذاتي كحاوية Docker على أي خادم خاص.

## متطلبات النظام والأوامر

### المتطلبات الأساسية
- **Node.js:** إصدار `>= 24.12.0` (كما هو محدد في `package.json`).
- **Java:** إصدار `Java 21+` (مطلوب محليًا فقط لتشغيل محاكيات Firebase Emulators واختبار قواعد الأمان).
- **Firebase CLI:** مثبت ومسجل الدخول (`firebase login`) للتعامل مع النشر والمحاكيات.

### التثبيت والتطوير المحلي (Socket.IO)

```bash
# تثبيت الاعتماديات
npm install

# تشغيل بيئة التطوير (السيرفر على 3001 والواجهة على 5173 عبر Vite proxy)
npm run dev
```

افتح `http://localhost:5173` في المتصفح. السيرفر على بورت `3001` ويقوم Vite بتمرير طلبات `/socket.io` تلقائيًا من نفس الأصل لتفادي مشاكل الـ CORS. للعب مع أجهزة على نفس الشبكة المحلية، افتح `http://<ip-الكمبيوتر>:5173`.

### تشغيل الاختبارات

```bash
# اختبارات الوحدة والمحرك وبنك الأسئلة
npm test

# اختبار قواعد أمان Firebase عبر المحاكي المحلي (يتطلب Java 21)
npm run test:firebase:rules

# اختبار المحاكيات الكامل (Auth + Realtime Database)
npm run test:emulator
```

### البناء والنشر لنسخة Firebase Spark

```bash
# بناء حزمة الويب لنسخة Firebase (تُخرج الملفات في apps/web/dist)
npm run build:firebase

# نشر القواعد والواجهة على مشروع Firebase المعتمد (yalla-nelaab-20261016)
npm run deploy:firebase
```

أمر `deploy:firebase` ينفذ صراحة:
`firebase deploy --only hosting,database --project yalla-nelaab-20261016`

**عند نشر التحديث الحالي:** انشر قواعد قاعدة البيانات الجديدة قبل الواجهة، واطلب من اللاعبين تحديث التابات المفتوحة قبل دخول غرف جديدة. الواجهة الجديدة تدعم الغرف القديمة أيضًا. تفاصيل المراحل في [سجل تنفيذ الترقية](docs/implementation/upgrade-progress.md)، ونتائج النشر والفحص في [سجل الإصدار](docs/verification/release-2026-10-18.md). بعد البناء، شغّل `npm run bundle:check` للتحقق من حدود حجم JavaScript.

### إعدادات الـ SDK العامة والأمان
متغيرات البيئة الخاصة بـ Firebase Web SDK (الموجودة في `.env.example` و`apps/web/.env.firebase`) مثل `VITE_FIREBASE_API_KEY` و`VITE_FIREBASE_PROJECT_ID` هي **معرفات عميل عامة** تُضمّن علنًا في كود الواجهة وليست أسرار إدارة خادم. أمان البيانات وصلاحيات القراءة والكتابة محكومة بالكامل عبر القواعد المشددة في `database.rules.json` ورموز التوثيق المجهول.

## المعمارية السحابية وحدود التشغيل (Firebase Spark)

في وضع Firebase Spark، يعمل النظام وفق نموذج استضافة المتصفح (Host-Browser Engine) الخاضع للضوابط التالية:

1. **محرك اللعبة داخل متصفح الهوست (Trusted-Friends Model):**
   - متصفح الهوست الحالي هو العقدة التنفيذية التي تدير محرك اللعبة، وتستقبل أوامر اللاعبين وتحسب النتائج. الغرف الجديدة تنشر الحالة المشتركة مرة واحدة في `publicView` والحالة الخاصة لكل لاعب في `privateViews/$uid`؛ الغرف القديمة تستمر بتنسيق `views/$uid` حتى تنتهي.
   - **الحدود الأمنية للمحتوى:** نظرًا لأن متصفح الهوست يحتفظ بلقطة الماتش الكاملة (`snapshot`) لتقييم الإجابات، فإن الهوست لديه إمكانية فنية لرؤية الأسئلة والإجابات عبر أدوات المتصفح. لذا فالمنصة مخصصة للعب الودي والموثوق بين الأصحاب، وليست موجهة لمسابقات عامة بين غرباء تتطلب مكافحة غش خادمية صارمة.
2. **نقل الاستضافة تلقائيًا:**
   - عند مغادرة الهوست أو انتهاء إيجار تشغيله، يحاول أقدم عضو متصل استلام الاستضافة بإيجار جديد ورقم `epoch` أعلى، وتُحدّث `meta/hostUid` والأدوار.
   - الهوست السابق يرجع إلى مقعده كعضو عادي. إبقاء الشاشة نشطة يساعد الاستقرار، ويُطلب قفل الشاشة أثناء الماتش عندما يدعمه المتصفح.
3. **الانتظار والاسترجاع:**
   - نبضات الهوست تراقب الاتصال، مع تنبيه بعد نحو 15 ثانية وحد استعادة إيجار منتهٍ مدته 60 ثانية.
   - الانقطاع المؤقت يحتفظ بمقعد اللاعب خلال مهلة 90 ثانية بدل إنهاء ماتش من لاعبين فورًا. الجولة تتقدم بمجرد اكتمال إجابات المشاركين المتصلين.
   - إجابة أثناء انقطاع قصير تُحفظ لمدة ثانيتين كحد أقصى، وتُراجع الجولة والمرحلة والسؤال على السيرفر قبل إعادة الإرسال.
4. **انتهاء الصلاحية خلال 6 ساعات (Six-Hour Expiry):**
   - تنتهي صلاحية أي غرفة أو كود تلقائيًا في قواعد الأمان بعد 6 ساعات كحد أقصى من إنشائها (`expiresAtMs <= createdAtMs + 21,600,000`).
5. **سعة اللاعبين والحد التاريخي التراكمي للغرفة (Capacity Limits):**
   - **اللاعبون النشطون:** 8 لاعبين كحد أقصى متصلين بالغرفة في نفس اللحظة (`memberCount <= 8`).
   - **الحد التراكمي للغرفة:** تطبق قواعد الأمان حدًا أقصى صارمًا لقبول اللاعبين هو 32 مقعدًا تاريخيًا تراكميًا لكل غرفة (`admittedCount <= 32` عبر 32 خانة في `memberSlots`). الغرفة التي تستنفد 32 عملية قبول عبر تاريخها لا تستقبل أي لاعب جديد لمنع التراكم غير المحدود.
6. **حدود اتصالات خطة Spark (100 Concurrent Connections):**
   - تضع خطة Spark سقفًا أقصى هو 100 اتصال متزامن في نفس الوقت لقاعدة البيانات على مستوى المشروع بالكامل. هذا يجعل البيتا ملائمة للمجموعات الخاصة الصغيرة من الأصدقاء.
7. **إدارة وحذف السجلات منتهية الصلاحية:**
   - خطة Spark لا تحتوي على وظائف سحابية مجدولة أو مسح TTL تلقائي.
   - عند إنشاء غرفة جديدة، يُحذف سجل الغرفة السابقة المملوكة لنفس الهوست إذا كان منتهيًا منذ أكثر من ساعة. هذا تنظيف محدود عند الاستخدام، وليس مسحًا دوريًا لكل الغرف.
   - يتم تفريغ السجلات المنتهية يدويًا عند الحاجة عبر Firebase Console أو Firebase CLI بحذر.
   - **قاعدة أمان حرجة (معتمدة ومستقرة):** لا يجوز حذف عقدة كود `/codes/<CODE>` لمجرد انتهاء غرفة قديمة؛ فالأكواد المكونة من 5 حروف قابلة لإعادة التعيين لغرف جديدة حية. يجب التفتيش أولاً والتأكد من أن الكود لا يزال مرتبطًا بنفس الغرفة المنتهية (`roomId`) قبل حذفه، مع حظر حذف الشجرة الجذرية (`/rooms` أو `/codes`) نهائيًا.
8. **حالة الإطلاق وبوابات التحقق:**
   - تكامل طبقة النقل عبر Firebase وربط دورة حياة التطبيق يخضعان لخطوات فحص ومراجعة مستمرة ونشطة.
   - وجود ملفات البناء الثابتة لا يعد وحده دليلاً على اكتمال التشغيل السحابي.
   - راجع وثيقة أهداف وتصميم الإطلاق في [`docs/WEBSITE-BRIEF.md`](docs/WEBSITE-BRIEF.md).
   - راجع خطة الفحص الميداني على أجهزة Android وiPhone في [`docs/BETA-PLAYTEST.md`](docs/BETA-PLAYTEST.md).

## تجربة اللعب الجماعي

المقعد النشط متخزّن في `sessionStorage`، يعني **كل تاب لاعب لوحده**. نسخة استرجاع مستقلة لكل مقعد في `localStorage` تنتهي بعد 15 دقيقة من آخر تحديث؛ إغلاق التاب ثم فتح الموقع يعرض زر الرجوع للماتش. هوية Firebase المجهولة محفوظة لكل مقعد، ويُفحص وجوده في تاب آخر قبل استرجاعه:

- **على نفس الكمبيوتر:** افتح تاب لكل لاعب على `http://localhost:5173`. واحد يعمل غرفة، والباقي يدخلوا بالكود. الـ refresh بيرجّع المقعد عادي.
- **على الموبايلات (التجربة الحقيقية):** كلهم على نفس الويفي، وافتحوا `http://<ip-الجهاز>:5173`.
- **من بره الشبكة (للتطوير):** `npx cloudflared tunnel --url http://localhost:5173`

## أنواع الجولات (18 لعبة متكاملة)

كل نوع سقفه الأساسي **200 نقطة** قبل وزن الجولة وكارت الكابتن. كارت الكابتن يضاعف النقط الموجبة في جولة واحدة، والفار يحذف اختيارين غلط أو يعطي نطاقًا للرقم؛ كل كارت متاح مرة واحدة في الماتش.

| اللعبة | الآلية | الطريق للـ 200 |
|---|---|---|
| سباق الإجابات | 4 اختيارات للكل في نفس اللحظة | 120 صح + لحد 80 سرعة (أول 3 ثواني مجانًا) |
| خمّن التاريخ | إدخال رقمي حر | مضبوط 200، وإلا ترتيب بالأقرب 150/110/80/50/25 |
| صح ولا غلط | 5 عبارات في 24 ثانية | +40 لكل صح، **−20 لكل غلط** |
| الكلمة الناقصة | كتابة حرة | 150 صح + لحد 50 سرعة (أول 6 ثواني مجانًا) |
| الكذّابين | اكتب إجابة مضروبة، وبعدين اعرف الصح من وسط الكذب | 100 للصح + لحد 100 على اللي وقعوا فيها |
| مين فينا؟ | صوّت على لاعب — مفيش إجابة صح | على قد ما رأيك يوافق الجماعة |
| مين أنا؟ | تلميح كل 9 ثواني | 200 / 150 / 100 / 50 حسب بدري خمّنت إمتى |
| رتّب صح | رتّب 4 حاجات بالترتيب الصح | 50 لكل حاجة في مكانها |
| السرقة | جاوب صح، وبعدين اسرق من حد شايفه غلط | 120 صح + 80 سرقة ناجحة، **−40 لو فشلت** |
| المزايدة | قول هتجاوب كام من 4 قبل ما تشوفهم | وصلت = المزايدة × 50، قصّرت = **صفر** |
| قطع الأرض | شبكة 3×3 (أو 4×4 فوق 5 لاعيبة) | 180 على الأرض + 20 للخط |
| وصّفهالي **(فرق بس)** | واحد من الفريق بيوصف والباقي بيخمّنوا | أول فريق 200، اللي بعده 130 |
| الدخيل | تلات ألغاز على الشاشة مرة واحدة، دوس على الغريب في كل واحد | 67 + 67 + 66 = 200 |
| إيموجي | لغز إيموجي واحد ع الشاشة، اكتب الإجابة، اتحل يعدّي للي بعده | 40 × 5 لغز = 200 |
| السلّم | سؤال اختيارات في كل درجة، صح = تطلع، غلط = **تقع لصفر وتخرج** | درجات [25, 60, 110, 155, 200] |
| أعلى ولا أقل؟ | سؤالين رقميين جنب بعض من غير إجاباتهم، اختار الأكبر | 50 لكل زوج × 4 أزواج = 200 |
| التتابع **(فرق بس)** | كل فريق بيطلع سلم أربع درجات بأسئلة الفريق التاني مش شايفها | فريق كامل = 200، جزئي = نسبي بعدد الدرجات |
| اسم حيوان جماد بلاد | حرف عشوائي، املا 4 خانات، وبعدين صوّتوا على إجابات بعض | 50 لكل خانة (30 صح + 20 تفرّد) × 4 = 200 |

الجولة الأخيرة دايمًا **×2 (سؤال الحسم)**، والتعادل على المركز الأول بيتحل بسؤال موت مفاجئ.

**طول الماتش تقريبي مش مظبوط:** الألعاب الطويلة (قطع الأرض، الكذّابين، المزايدة) بتاخد خانتين من ميزانية الجولات لأنها فعلًا بتاخد وقت جولتين — فماتش «متوسط» ممكن يطلع ٨ جولات مش ١٠. الواجهة بتوضح ده بصراحة.

## غرفة لحد 8 لاعبين

الحد الأقصى للغرفة **8 لاعيبة**، ومتعرّف كقيمة مركزية في `packages/shared/src/match.ts` لتطبيقه في اللوبي وقواعد الأمان:

- **قطع الأرض بتكبر مع الغرفة:** تسع مربعات على تمن لاعيبة يعني مربع للواحد، فالبورد بيكبر تلقائيًا إلى **4×4** فوق 5 لاعبين لضمان المنافسة.
- **الكذّابين بتاخد وقت تصويت ديناميكي:** قايمة التصويت سطر لكل لاعب + الإجابة الصح، والوقت محسوب من عدد الاختيارات.
- **السرقة ومين فينا وقتهم محسوب:** سبع أسامي تتقري أهدى من تلاتة لمنح فرصة عادلة للجميع.
- **ألوان المقاعد:** كل مقعد ليه لون مميز وثابت يظهر في اللوبي، وبورد قطع الأرض، وقوائم الترتيب لتمييز اللاعبين بصريًا بسرعة.

## المسافة بين الجولات

النقاش والضحك بعد الجولة جزء أساسي من القعدة:
- شاشة النتيجة مدتها الأساسية **11 ثانية** وتتفاوت بحسب طبيعة اللعبة (`revealWeight`). فالكذّابين بتاخد وقتاً أطول لكشف من خدع من، وسباق الإجابات يمر أسرع.
- يملك الهوست زرار **«يلا كمّلوا»** لاختصار وقت النتيجة والانتقال للجولة التالية فور انتهاء الحوار. الجولة الحية لا يمكن تخطيها أثناء إجابة اللاعبين.

الماتش الكامل (15 جولة) يستهلك نحو 23 سؤال اختيارات في غرفة من 6 لاعبين. لذا يحظى كل مجال (عدا مين فينا الموجهة للأشخاص) بـ **230 سؤال اختيارات** لتمكين مجموعات اللعب من خوض عدة ماتشات متتالية دون أدنى تكرار.

### ما تحرسه الاختبارات الآلية
- كل مجال قادر بمفرده على تشغيل كافة الألعاب المؤهلة **4 مرات** على الأقل دون تكرار (و**3 مرات** لمجال «مين فينا» الذي يملك بروفايلاً أصغر بتصميم متعمد).
- بكل المجالات مجتمعة، كل نوع جولة يشتغل **25 مرة** من غير تكرار (`word_race` عند 15 مرة لأنه يعيش في «مين فينا» فقط).
- بنك الأسئلة يخضع لفحص تشابه نصي متقدم (`apps/server/src/content/json-source.test.ts`) يمنع وجود سؤالين يحملان نفس الفكرة بصياغتين مختلفتين حتى عبر المجالات المتعددة.

---

## مود الفرق

- يقسم الهوست الغرفة إلى فريقين متوازنين يتوزع عليهما الأعضاء تلقائيًا.
- **نقط الفريق = متوسط نقط أعضائه وليس المجموع:** لمنع فوز الفريق الأكثر عددًا تلقائيًا عند تفاوت الغرفة (مثل 3 لاعبين ضد 2).
- **فك التعادل:** يتم بين الفرق بالكامل، ولا تتدخل النتيجة الفردية للاعب داخل الفريق الفائز في حسم نتيجة الفريق.

## معمارية الكود والتصميم

```
packages/shared    الأنواع، ومخططات Zod، وحساب النقط والترتيب العام
packages/rounds    منطق الـ 18 لعبة كدوال نقية (Reducers) بدون I/O
apps/server        محرك الغرف المحلي وسيرفر Socket.IO
apps/web           واجهة React عربية RTL ومكونات التجربة وشاشات اللعب
content/seed       بنك الأسئلة المعتمد (ملفات JSON)
```

### مبادئ تقنية أساسية
1. **ألعاب كـ Pure Reducers:** كل لعبة في `packages/rounds` عبارة عن دوال حالة نقية تمامًا، والوقت يدخل كبيانات، مما يجعل منطق اللعب قابلاً للاختبار والمحاكاة بنسبة 100% سواء كان النقل عبر Socket.IO أو متصفح الهوست.
2. **سقف الـ 200 نقطة محمي باختبار:** ملف `invariants.test.ts` يختبر كل لعبة بمحاكاة عشوائية ومثالية للتأكد من استحالة تجاوز سقف الـ 200 نقطة.
3. **الفصل بين `version` و `roundNo`:**
   - `version`: عداد يتزايد مع كل عملية تحديث للحالة لمنع تضارب التزامن في الـ Store.
   - `roundNo`: عداد يتزايد عند بدء جولة جديدة فقط لحراسة استلام إجابات اللاعبين ومنع ضياع الإجابات المتزامنة.
